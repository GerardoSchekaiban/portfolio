Enterprise configuration data product: a medallion architecture

Enterprise configuration data (sites, accounts, nodes, software, entitlements) is scattered across dozens of operational tables. This project designs a medallion architecture that turns those raw extracts into three reusable data products. Each layer has one job, and quality checks run before the next layer does.

  1. S

    Situation

    Raw configuration data was being ingested from an enterprise IT service platform, but it was unmaintained and had no access layer. Business users could not query it.

  2. T

    Task

    I owned the full lifecycle of the authoritative configuration data products: missing ingestion, data-gap fixes, layered architecture, quality checks, metadata governance and stakeholder enablement.

  3. A

    Action

    I designed and built three data products (site, node and summary configuration), each with a current and a history view, on a raw → transform → access architecture. Every object passed a formal governance certification before release.

  4. R

    Result

    Six certified data objects, used by more than 100 people a month and now feeding agentic AI use cases across the organization.

    Key decisions

    Five choices that shape the design, and what each one costs. Click a decision to expand it.

    BronzeI kept sources exactly as received: no business logic, only load metadata.

    Why: Any run can be replayed, and a bad rule can never corrupt the raw copy.

    Trade-off: Raw noise (duplicates, coded values) is stored and handled later.

    SilverI defined each business entity once, in silver.

    Why: Every product reads the same site, node and account definitions.

    Trade-off: Silver changes need care, because every gold product depends on it.

    SilverI put heavy logic in tables and light logic in views.

    Why: Expensive steps (site, node, lookup) run once per load, while simple ones stay fresh with no storage.

    Trade-off: Tables add refresh steps and storage.

    GoldI kept history as SCD Type 2, with a current view on top.

    Why: A full audit trail, and the current view always returns one row per site.

    Trade-off: More rows, and a close-and-open step on every change.

    All layersI made a failed quality gate keep the previous version live.

    Why: Consumers get data that is a day old but correct, instead of fresh but wrong.

    Trade-off: A persistent failure leaves data stale until someone fixes it.
